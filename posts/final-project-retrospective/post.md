## 들어가며

파이널 프로젝트는 문구 이커머스 플랫폼을 팀으로 만드는 프로젝트였다. 나는 마이페이지 영역(소비자 주문 내역·찜한 상품, 판매자 상품 등록·상품 관리·상점 주문 관리)을 맡았다.

프로젝트 기간 동안 거의 매일 개발 일지를 썼다. 이 글은 그 일지들을 다시 읽으며 정리한 회고다. 무엇을 만들었는지보다, 그 과정에서 무엇을 이해하게 되었고 어디서 막혔는지를 중심으로 적었다.

## 기술적으로 배운 것

### 1. 역할에 따라 파일의 책임을 나누기

퍼블리싱 첫날 가장 먼저 정리한 원칙은 "조건은 page에서, UI는 컴포넌트에서"였다.

- `layout.tsx` — 사이드바처럼 페이지가 바뀌어도 유지되는 전체 틀
- `page.tsx` — 이 페이지에서 무엇을 보여줄지 판단 (데이터 유무, USER / BUSINESS 역할 분기)
- `components` — 실제 화면을 구성하는 재사용 가능한 조각

이후 마이페이지를 `mypage/consumer`와 `mypage/seller`로 나누고 각 `page.tsx`를 서버 컴포넌트로 구분하면서, 이 원칙이 폴더 구조로도 이어졌다. 멘토 선생님께 페이지 구성 방식을 확인받은 뒤에는 확신을 가지고 컴포넌트를 조립할 수 있었다.

### 2. DB 값과 화면에 보여줄 라벨을 분리하기

처음에는 DB에 저장된 값과 화면에 보여주는 한국어를 섞어서 사용했다. PR 리뷰에서 이 부분을 지적받았고, DB 키 이름과 타입을 통일하는 리팩토링을 진행했다.

DB에는 영문 키로 저장하고, 화면에 표시할 한국어 라벨은 별도의 매핑 객체로 관리하도록 바꿨다. 이렇게 하면 데이터의 일관성을 지키면서 표시 문구는 독립적으로 수정할 수 있다. 개발 서버에서 문제없이 보인다고 해서 올바른 구조는 아니라는 것을 이때 처음 체감했다.

### 3. 복잡한 폼 상태는 커스텀 훅으로 모으기

상품 등록 폼은 입력 항목마다 타입과 검증 조건이 달라서 상태 선언이 빠르게 늘어났다. 이를 커스텀 훅으로 분리해 관리했고, 페이지네이션과 탭 정렬도 같은 방식으로 커스텀 훅으로 빼내 컴포넌트에 바로 연결할 수 있게 만들었다.

부모에게서 받을 props, 자식이 발생시킬 이벤트, 둘을 잇는 흐름을 설계하는 과정이 처음에는 낯설었지만, 반복할수록 조금씩 패턴이 보이기 시작했다.

### 4. Server Action과 Supabase

상품 등록 기능을 Server Action으로 구현하면서 다음을 알게 되었다.

- Server Action에서 FormData로 파일 업로드를 처리하는 방식
- Server Action을 쓰면 form의 `method`, `encType`을 따로 지정하지 않아도 된다는 점
- Supabase RLS(Row Level Security) 정책에 따라 insert가 막힐 수 있다는 점
- `store_id`는 사용자가 입력하는 값이 아니라, 로그인한 사용자로부터 상점을 조회해 연결해야 하는 값이라는 점

### 5. TanStack Query와 URL 상태 관리

찜한 상품 목록을 Supabase와 연동하면서 TanStack Query를 적용했다. 서버 데이터를 캐싱하고, 삭제 후 목록을 자동으로 다시 불러오도록 처리했다. 로딩 상태를 제공하는 기능과, `useMutation`처럼 데이터 변경과 성공·실패 처리를 한곳에서 다룰 수 있는 구조도 이때 익혔다.

카테고리, 정렬(최신순, 가격 높은 순, 가격 낮은 순), 페이지 상태는 URL query string으로 통합해 관리했다. 새로고침하거나 페이지를 이동해도 상태가 유지된다. 카테고리 탭도 고정 배열 대신 DB 데이터를 기반으로 생성하도록 바꿔, 데이터가 바뀌어도 UI를 따로 수정하지 않아도 되게 했다.

### 6. 접근성

`LikeToggleButton`과 `Pagination` 컴포넌트에 `aria-hidden`, `aria-label` 속성과 hover 스타일을 추가했다. 리스트는 `ul`, `li`로 마크업하는 것처럼 기본적인 시맨틱 구조도 컴포넌트를 만들 때마다 다시 확인했다. 또 타이머 값처럼 렌더링과 무관하게 유지해야 하는 값은 `useRef`로 보관할 수 있다는 것도 이 시기에 배웠다.

## 트러블슈팅

### Supabase join 결과의 타입 불일치

**문제**
주문 상품 목록을 연동하는 과정에서 에러가 발생했는데, 데이터가 여러 컴포넌트를 거쳐 전달되고 있어 어느 지점에서 발생한 문제인지 파악하기 어려웠다. 컴포넌트 구조를 몇 차례 바꿔 봐도 해결되지 않았다.

**원인**
문제는 컴포넌트가 아니라 데이터를 받아오는 단계에 있었다. `order_items` 하나에는 상품 하나가 연결되지만, join 결과의 TypeScript 타입은 배열로 잡혀 있었고 실제 데이터와 타입이 일치하지 않았다.

**해결**
데이터를 불러오는 함수의 반환 타입을 명시적으로 지정했다. 이후 데이터가 의도한 형태로 전달되었다.

**배운 점**
에러 위치를 컴포넌트에서만 찾지 말고, 데이터가 들어오는 입구부터 확인해야 한다는 것. 그리고 TypeScript는 타입을 원하는 대로 조립할 수 있는 만큼, 실제 데이터 형태를 정확히 알고 있어야 한다는 것.

### 옵션 입력 에러 메시지가 사라지지 않는 문제

**문제**
상품 등록 폼에서 제출 버튼을 누르면 옵션 관련 에러 메시지가 표시되는데, 이후 옵션을 추가해도 메시지가 사라지지 않았다.

**원인**
옵션 에러 상태를 `clientErrors.productOptions`와 `useOptionForm`의 `error` 두 곳에서 따로 관리하고 있어 상태가 동기화되지 않았다.

**해결**
옵션 관련 에러 상태를 `useOptionForm` 내부의 `error` 하나로 통합했다. 옵션 추가 버튼의 검증과 제출 버튼의 검증이 모두 같은 `setError()`를 통해 상태를 변경하고, 옵션 추가에 성공하면 에러를 초기화하도록 수정했다.

**배운 점**
같은 의미의 상태를 여러 곳에 두면 동기화 문제가 생긴다. 일반 폼 검증과 옵션 검증의 책임을 나누고, 각 상태는 한 곳에서만 관리하는 것이 흐름을 단순하게 만든다.

## 코드 리뷰와 멘토링에서 얻은 것

PR을 올리면 웬만하면 승인되겠지 생각했지만, 팀원분이 수정하면 좋을 부분을 구체적으로 남겨주셨다. 수정할 코드를 찾고, 이해하고, 질문하는 데 하루 수업 시간이 다 지나갔지만 그 과정에서 DB와 화면의 기준을 분리하는 방법을 제대로 배웠다.

멘토링에서는 코드의 흐름을 이해하고, 내가 쓰는 기술에 대한 지식을 갖춰야 한다는 피드백을 받았다. 정해진 기간 안에 사이트를 완성하는 데 집중하다 보니 기술을 왜 선택했는지, 어떤 특징이 있는지에 대해서는 제대로 설명하지 못한다는 것을 인정할 수밖에 없었다.

또 하나 느낀 것은, 내가 지금 어떤 문제를 겪고 있고 무엇이 궁금한지를 언어로 정리하는 것 자체가 쉽지 않은 일이라는 점이다. 좋은 질문을 하는 것도 실력의 일부였다.

## 마음가짐의 변화

프로젝트 첫날 일지에는 걱정이 가득했다. 실력 있는 팀원들 사이에서 내가 폐가 되지는 않을까, 이 시장에서 일할 수 있는 사람인가 하는 의구심이 컸다. 개발 첫날에도 속도가 느려서 정해둔 범위를 다 구현하지 못할까 봐 불안해했다.

중간점검은 전환점이었다. UI 작업을 먼저 하고 Supabase 연동을 뒤로 미뤘던 탓에 보여드릴 수 있는 로직이 많지 않았고, 남은 시간이 많지 않다는 것을 그제서야 실감했다. 그 뒤로는 쉬는 날과 주말에도 코드를 작성했다.

그리고 어느 순간부터 일지에 다른 문장이 등장하기 시작했다. 데이터 연결에 성공해 화면에 나타났을 때의 짜릿함, 콘솔에서 복잡한 데이터가 제대로 들어오는 것을 확인했을 때의 뿌듯함, 직접 등록한 상품이 개발 서버에 올라오는 게 신기해서 몇 개를 더 올려본 일. 만들 때는 힘들어도 완성하고 나면 "내가 이걸 재밌게 하고 있었구나" 싶었다.

모르는 것, 이해되지 않는 것의 답은 결국 반복이라는 것. 이 프로젝트에서 얻은 가장 큰 확신이다.

## 남은 과제

- **상품 등록 폼 리팩토링** — 입력 검증 때문에 대부분 클라이언트 컴포넌트로 만들어졌다. 서버 컴포넌트를 활용하는 구조로 개선하고, 클라이언트·서버 검증의 역할을 명확히 정리하기
- **설명할 수 있는 코드** — 상품 등록 로직은 도움을 받아 완성한 부분이 많아서 팀원에게 설명하기 어려웠다. 직접 다시 짜 보며 흐름을 내 것으로 만들기
- **기술 선택의 이유** — 사용한 기술에 대해 10가지를 물으면 5가지 이상은 명확하게 답할 수 있도록 지식을 쌓기
- **작업 순서** — 다음 프로젝트에서는 더미 데이터에 오래 의존하지 않고, 실제 DB 스키마를 기준으로 데이터 연동을 더 일찍 시작하기

## 마치며

3주 남짓한 시간 동안 가장 많이 쓴 단어는 "어려웠다"였지만, 그 어려움을 하나씩 기록하고 다시 들여다본 덕분에 무엇을 배웠는지 선명하게 남길 수 있었다. 부족함을 인정하는 것에서 멈추지 않고, 그 부분을 조금이라도 덜 부족하게 채워가는 개발자가 되고 싶다.
